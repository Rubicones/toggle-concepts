## 2. Summary of Changes

Why: in bench run 2 the designer wrote `Frame.tsx` whole on all seven of its building turns, 3,500 to 9,800 output tokens each, mostly to change a few lines. Output is the dearest part of a turn.

- `packages/director/hero-chat.ts`
  - `parseChatAnswer(text, schema, {edits})`: with `edits` on, a fenced block opened with `edit` and a path is read as one exact edit. Without it (version 5 and lower) the answer is read as before.
  - `applyEdits(files, edits)`: applies edits in order to the files as they stand. Returns the changed files, whole, and one line per refused edit.
  - `usesEdits(input)`: true from designer version 6.
  - `EDITS_NOTE`: the wording of the format, said once in the hero task and once in the stage E opening.
- `packages/director/extension-chat.ts`: the stage E opening carries `EDITS_NOTE` in version 6, so a condensed conversation still knows the format.
- `apps/local-runner/director/hero-chat-loop.ts`, `extension-chat-loop.ts`:
  - Whole files of an answer are written first, then its edits in the order written.
  - A changed file triggers the build and the render, as a whole file does.
  - A refused edit is said in the next message; the other edits of the answer still apply.
- `scripts/bench/pipeline-bench.ts`: the summary now holds `designerOutputPerTurn` and `edits` (edit blocks applied, turns with a refused edit), which is what the owner's test reads.

### Application rules (plan 4b)

| Case | What the app does |
|---|---|
| The current text is in the file exactly once | Replaced. The replacement is taken literally. |
| The current text is not in the file | Refused: "An edit to Frame.tsx was not applied: its current text is not in the file as written. The nearest lines in the file now:" followed by up to three current lines |
| The current text is in the file more than once | Refused: "…its current text is in the file N times; include more of the text around it so it is found once." |
| The file does not exist | Refused: "…there is no such file yet; write it whole." |
| The block has no line of `=======`, or more than one | Refused, with that reason |
| A later edit of the same answer | Applied to the file as the earlier edits left it |
| A whole file and edits in one answer | Whole files first, then edits |

## 3. Self-Review & Risk Audit ("Can It Produce Another Bug or Blocking Error?")

1. **Frozen `config_hash`, `requestId`, `quoteId` on active runs:** no. The reader's new branch and the new paragraph are behind `designerVersion >= 6`. The version 5 hero task and stage E opening are pinned by hash in `tests/e1-hero-meaning.test.ts` and still match.
2. **`DRAFT_INPUT_CAP` and schema limits:** the hero task grows by about 560 characters. No schema changes. Output per turn should fall; that is the point.
3. **`AGENTS.md` principles:** the paragraph describes a format and holds no layout, style or name. No paid call. Approved copy is not touched by the app: an edit changes only the text the designer quotes.

Risks that remain:

- **Not measured yet.** No live run has used edits. The saving in output tokens and the rate of refused edits are unknown until run 3.
- **A refused edit costs a turn of intent.** The designer's change is not in the render it sees next. The message quotes the nearest lines so the next attempt can match.
- **A code line of `=======`** inside the quoted text would split the block wrongly. The block is then refused with a reason, not misapplied.
- **A fenced block inside the quoted text** (three backticks in the code) ends the edit block early. The file is then not changed and the edit is refused.
