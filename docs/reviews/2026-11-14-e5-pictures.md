## 2. Summary of Changes

### 2.1 The picture hold (plan E5)

**The evidence.** In both live bench runs the designer asked for a picture and wrote a stand-in in the same answer. The picture landed one or two turns later, and the renders in between showed the stand-in. In run 1 the hero was accepted on a stand-in.

- `apps/local-runner/director/hero-chat-loop.ts`
  - In version 6, when an answer changed the code and a picture is still being made, the render waits for it, for at most `PICTURE_HOLD_MS` (180 s).
  - When the picture arrives, the code is built again, because the picture changes `resources.ts`, and then rendered.
  - The render message says which pictures arrived and are in the render, or that a picture was not ready in time. A picture announced this way is not announced again later.
  - `state.pictureWaitMs` adds up the time waited.
- `packages/director/hero-chat.ts`: the "PICTURES" paragraph of the version 6 hero task now states the hold and names the ids the pictures will have, in order. `pictureWaitLine` is the timeline's line.
- `apps/local-runner/director/worker.ts`: the timeline shows "Waiting for the picture for the key frame (up to 180 s)."
- `scripts/bench/v5-direction.ts`, `pipeline-bench.ts`: the bench runs the same loop, so it holds the same way. `--hold=<seconds>` changes the bound; the summary holds `pictureWaitSeconds`.

**The bound is a starting value.** On the bench a picture delivered by hand took 40 to 120 s. How long a picture bought in production takes is not measured: the export of the live run holds no picture purchase. The plan asks for "usually about N s" on the timeline; without a measured N the line says "up to 180 s" instead.

**Stage E is not changed.** The plan names stage H only.

### 2.2 Measured facts about logos and brand pictures

**The defect.** A logo record in the block's input holds an id, a file name and a clear space. In run 2 the designer spent turns 3, 4 and 8 telling a navy wordmark from a white one: by matching words in records, then by asking for a kit section, then by rendering a sheet of all eight logos.

- `apps/local-runner/director/logo-facts.ts` (new)
  - `measureLogo`, `measureLogos`: for each supplied logo file, the colour and lightness of the drawing, whether the ground is transparent, the logo's own ground if it has one, its proportions, and which grounds it reads on.
  - `logoFactLines`: one line per logo, with the catalogue name of the same material when there is one.
  - `referenceFactLines`: one line per brand reference picture: its catalogue name and kind, its size and its ground.
- `packages/director/designer-digest.ts`: in version 6 the "BRAND IN CODE" section lists these lines instead of "brand.logos[0] (clear space 0 px), …".
- `apps/local-runner/director/worker.ts`, `scripts/bench/v5-direction.ts`: measure once per direction and pass the lines to the designer's digest.

On the export's eight logo files the lines are exact: two white wordmarks "read on dark grounds", two navy and three black marks "read on light grounds". That was checked locally; the files are not in the repository.

**No kit helper.** A helper that picks the mark in code needs the facts in a generated file of the draft folder. That file would have to be added to four lists of app-owned files and to the sealing of a draft. It is not cheap, and the lines already say which mark reads on which ground.

### 2.3 The hero review sees the frame at thumbnail size

- `apps/local-runner/director/worker.ts`, `scripts/bench/v5-direction.ts`: in version 6 the hero review gets a second picture, the same render at 180 px. Four of its checks name thumbnail size; until now the reviewer imagined it from the full-size render.

### 2.4 Every changed text, before and after (version 6 only; for the owner's approval)

**The "PICTURES" paragraph of the hero task.**

Before (committed in `bc003ec`):

```text
PICTURES
You may ask for up to N pictures in this direction, for all its scenes together. A picture takes a minute or more to make and arrives in a later message, not in the next render: ask for the ones this frame needs in the same answer as your first build, and build the frame so the picture takes its place when it arrives.
```

After:

```text
PICTURES
You may ask for up to N pictures in this direction, for all its scenes together. In the order you ask, they are resources['<id 1>'], resources['<id 2>'], …. When an answer asks for a picture and changes the code, its render waits for the picture (up to about 3 minutes), so you see the frame with the picture in place: ask for the pictures this frame needs in the same answer as the code that draws them.
```

**The render message.**

| When | Before | After |
|---|---|---|
| A picture arrived during the hold | (next turn) `The picture <id> has arrived: read resources['<id>'].` | `The picture <id> has arrived and is in this render: read resources['<id>'].` plus, with a cutout, `Its cutout is resources['<id>'].cutoutUrl.` |
| A picture was not ready in time | nothing | `One picture was not ready after 180 s: this render is without it, and it arrives in a later message.` |

**The "BRAND IN CODE" section of the digest.**

Before:

```text
Logos: brand.logos[0] (clear space 0 px), brand.logos[1] (clear space 0 px), …
```

After:

```text
The brand's own pictures (draw one with <Img src={staticFile(brand.references[n].url)}/>; used as supplied, never redrawn):

Logos (each supplied file as measured: the colour of its drawing, its ground, its proportions, the grounds it reads on):
- brand.logos[0] · <catalogue name> · drawing #FFFFFF (light) · transparent ground · 7.92:1 wide · reads on dark grounds · clear space 0 px
```

**The label of the second picture in the hero review.** Before: nothing. After: `The same hero frame at thumbnail size, as it appears in a feed`.

**The timeline.** New line: `Waiting for the picture for the key frame (up to 180 s).`

## 3. Self-Review & Risk Audit ("Can It Produce Another Bug or Blocking Error?")

**The hold.**

1. **Frozen `config_hash`, `requestId`, `quoteId` on active runs:** no. It is behind `designerVersion >= 6` and changes when a render runs, not what a request holds.
2. **Caps:** not affected. A hold adds waiting time, never a request. Local runs are bounded by tokens and requests, not by the clock.
3. **`AGENTS.md` principles:** no screenshot sweep is added: the hold replaces a render of a stand-in with one render that has the picture. Pictures are still bought inside the approved count, through the same ledger path.

Risks that remain:

- A slow picture service makes a hero turn up to three minutes longer per held render. The timeline says so.
- A picture that fails during the hold is said to have failed, and the render runs without it.
- The designer may still write a stand-in. The hold makes the stand-in unnecessary; it does not forbid it.

**Logo and reference facts.**

1. **Frozen digests:** no. The lines are added only in version 6. The version 5 digests are pinned by hash and still match.
2. **Caps:** the digest grows by one line per logo and per reference picture: about 4,000 characters for the export's 8 logos and 17 references.
3. **Principles:** the lines are measurements and the brand's own catalogue names, passed as data. Nothing is redrawn. A file that cannot be read is listed as "not measured".

Risks that remain:

- "Reads on" is derived from the lightness of the dominant colour of the drawing. A mark of two very different colours is listed with its dominant one and "2 colours".
- A mark with a filled shape that leaves less than 8% of its box clear is read as carrying its own ground.
- A reference's description comes from the catalogue and can be vague ("inferred from the file name"). It is cut at 70 characters.

**The thumbnail.**

1. **Frozen digests:** no; version 6 only.
2. **Caps:** one small picture more in the hero review.
3. **Principles:** it is the same render, smaller. No wording changes in the reviewer's instructions.
