## 1. Database Migrations to Apply (ACTION REQUIRED BY OWNER)

- **Migrations Added:** `supabase/migrations/20261111000400_skills_and_stage_effort.sql`. Apply it after `20261111000200` and `20261111000300`.
- **Why Needed:**
  - `studio_skill_attachments` (tenant, skill_id, role) records which roles each skill is attached to.
  - `studio_stage_effort` (tenant, stage, effort) holds the LC6 effort per stage.
  - `studio_skills_version()` lets the app check whether the migration is in place.
  - Both tables are service-role only (RLS on, no grants to browser roles).
- **How to Apply:**
  - Run `npx supabase db push`, or paste the file into the Supabase SQL Editor and run it. It is safe to run twice.
  - SQL test: `supabase/tests/skills-and-stage-effort.sql`, added to `scripts/verify-creative-migration.py`.
- **Backward Compatibility:**
  - Without the migration, Models & agents shows a notice and the runner reads "no attachments, default efforts".
  - Runs whose context is already frozen keep their skills; attachments are read only when a context is first frozen.
  - `fresh` and OpenRouter runs are unaffected.

## 3. Self-Review & Risk Audit

1. **Digests:**
   - Skills are added by the Local transport layout, after the prepared request is built.
   - `requestId`, `config_hash`, `quoteId` and the semantic hash are unchanged.
   - Adding role skills does not change the run context hash; a test checks this.
2. **Caps:**
   - Skills go into the CLI request only, which `DRAFT_INPUT_CAP` admission does not count.
   - The per-role limit is 6,000 tokens, which keeps them small.
   - No change to JSON schemas.
3. **`AGENTS.md`:**
   - The skills are principles only. A test rejects example wording, URLs, and font, brand or design-system names.
   - No layouts, no paid calls, and no change to approved copy.

**Known limit:** the role's own skills sit in the role part of the request, after the cached prefix. They are cached per role, not across roles.
